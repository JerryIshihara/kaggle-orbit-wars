## 1. What this is
**Kaggle "Orbit Wars"** ($50k RTS-agent competition, deadline 2026-06-23). We train the
`transformer_v2` agent's **PairHead** policy with **PPO**, split across machines:
- **Rollout actors** (GCP CPU VMs and/or the two M1 Macs) play self-play games → write replay **shards** to GCS.
- **Learner** (Colab GPU; or a Mac CPU for trials) consumes shards → PPO update → new policy.
- **Coordination** via one **Firestore** STATE doc (push); **big files on GCS**. Hands-off: each side polls/streams STATE and acts only on its phase.

## 3. Model + freeze phases
L0 encoders (planet/fleet/comet) → L1 → L2 cross → **L3 `dual_role`** → **L4 `joint_role`** → PairHead (trunk+FiLM → pair_logits + pair_frac). d_model=256, T=10, **no consolidator** → glob value head. **(⚠️ §9: eval shows the policy is far behind `physical_v4` — the glob value head is FRESH; a consolidator + `PairCompareHead` critic redesign is decided.)**
`freeze_for_phase`: **0** = heads+value (~395k); **1** = +trunk/FiLM+L4 (~2.0M); **2** = +L3 (~2.5M, head-delta ~10 MB). Use `--freeze-phase 2`; set `--lr-trunk` (e.g. 1e-5) < `--lr-heads` (1e-4) to protect the supervised backbone.

## 5. Hard-won facts / gotchas
- **orbit_wars RUNS on macOS arm64** (only unused `cabt` needs `libcg.so` — ignore that warning). A & B can be actors.
- **Games cap at ~500 steps** (1200 = the loop's safety `max_steps`, never hit). Iter wall ≈ longest ~500-step game × per-step.
- **T=10 shards ~1.5 GB/game** → big disk or upload-and-delete; the pool holds ~1.5 GB × M EpisodeBuffers in RAM (use roomy VM, n2 64 GB ok for 16).
- **FD bug (fixed):** the pool returning large tensors via torch's default `file_descriptor` sharing exhausted FDs → `OSError: Too many open files`. Fix: `set_sharing_strategy("file_system")` + `setrlimit(RLIMIT_NOFILE,hard)` + launch with `ulimit -n 1048576`.
- **Speed:** ~6–8 min/game (T=10, c4) / longer on n2. **1-game-per-core wins**; more cores = throughput not wall. Big lever = **lower T** or faster per-core (c4 ≈ 1.3× n2). Player-per-core does NOT help (env serializes per step).
- **Colab:** `subprocess.run` doesn't stream (use `Popen`+pipe); auth sets no project (`gcloud config set project`); runs as root.
- A **CPU-pegged VM refuses SSH (255)** → manage via API (`instances reset/stop`).
- **Don't kill an actor VM** unless its Firestore heartbeat stops or it errors (a mid-rollout VM with no `_DONE` yet is normal — `games_done` advances but shards flush at the end of the slice).
- **dynamic-OMP is FATAL with the fork pool (FIXED, keep it off).** `torch.set_num_threads(N>1)` inside a forked worker deadlocks OpenMP at the first forward. The straggler ramp sized the low-`remaining` tail games to 2/4/8 threads → they **froze at step 0** and hung the whole rollout (seen at 13/16, then 4/8). `pool_rollout` now pins every worker to **1 thread unconditionally** + `dynamic_omp` defaults **False**. Signature to recognize: workers `Sl`/idle, `load`≈1, `steps/s=0`, frozen cores show `t2/t4/t8` at `step=0`. Never re-enable dynamic-OMP under fork.
- **SSH host-key 255 after a VM `reset`/machine-image clone:** the host key changes → ssh refuses. Use `--ssh-flag="-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null"` (safe for our ephemeral VMs). Recurring 255s in a row = this, not load.
- **Stale `phase=error` blocks relaunch.** A VM `reset` (or any kill) of an in-flight rollout makes the daemon stamp `phase=error msg="rollout vK exited -9"` in Firestore; a relaunched daemon just reads ERROR and exits in ~1s. Clear it first: `transition(expect_phase=ph, new_phase=await_rollout, message="")`.
- **Pool fork-race at step 0 (transient):** forking 8 workers from a torch-loaded parent can occasionally wedge one VM at step 0 with `threads=1` (NOT the OMP bug). A clean daemon restart clears it (observed on the us-east1 clone; us-central1 was fine). If a VM sits at `games_done=0, cores=0` for minutes while its peer advances, just restart it.
- **Launch over SSH reliably:** long inline `--command` daemon launches flake; stage the launch as a script the VM pulls from GCS (`gs://…/tmp/remote_launch.sh`) invoked by a short SSH command, and retry. See `/tmp/orchestrate_launch.sh`.

## 9. Eval vs physical_v4 + critic redesign (2026-06-01)

### Eval — the learned policy is FAR behind physical_v4
`/tmp/eval_vs_physical.py <policy_vK.pt>`: loads a PPO ckpt (`load_supervised` scaffold + `pstate['policy']`, strict=False) → plays vs `physical_v4` via `smoke.run_episode(opponent_id='physical_v4')` on 5 eval-panel seeds. Sampled play (sigma=0.35):
- **policy_v2 (PPO): 0/5**, ~5 ships vs physical_v4's 1.5k–6.4k; near-passive (loses all planets by ~step 150).
- **policy_v0 (supervised base): 0/5**, 5–35 ships — also crushed.
NOT just PPO breaking a good policy: the **supervised PairHead is itself far below physical_v4**, and PPO made it slightly *worse* (v0 sometimes 24–35 ships; v2 flat ~5). Caveat: sampled (the official agent plays greedy via `run_match`) — greedy may be a touch better, but ~5 ships isn't sampling noise.

### Root cause of the PPO leg: the value head is FRESH
PPO runs `--no-consolidator` → the glob `value_head` (debug fallback, `allow_debug_glob_critic=True`, zero-init), NOT the pretrained `value_decoder`. Critic trained from scratch each run → huge value_loss → noisy/oversized advantages → policy flattens (entropy ~12.6) → early KL stop. **The pretrained critic was never used.**

### Pretraining labels (two CLIs, two caches)
- **Actor/PairHead** — `entity_encoder` on the **pair-cache** (`ActionSnapshotDataset`): expert `source_planet_idx`/`target_planet_idx`/`expert_acted`/`frac_label=ships_sent/source_ships`. Loss = CE/BCE over flattened (P×P) pair logits (`--pair-pos-weight 600`) + FracHead NLL. (Behaviour-clone the expert.)
- **Critic/value** — `cross_entity --head-set critic` on the **cross-cache**: `winner_seat`+`final_rank`+`is_ahead_t+h`. `value_decoder` trained by winner-BCE + ListMLE-on-rank; **is_ahead computed but UNUSED**.

### Critic redesign (DECIDED 2026-06-01 w/ user; NOT yet implemented)
Relative critic, re-grounded on is_ahead:
- **Drop** winner-BCE + ListMLE-rank.
- **Re-activate `is_ahead`** — per-player BCE on `is_ahead_t+h`.
- **Add `PairCompareHead`** — one shared MLP over `[player_state_i ‖ player_state_j ‖ glob]` (in=3·d_model) → 1 logit = P(player i outperforms j), over all valid ordered player pairs (from `PlayerConsolidator` `player_state (B,4,d)`, slot 0 = learner).
- **PPO V(s)** = `mean_j σ(pair_compare(slot0, slot_j))` over valid opponents (uniform 2P/4P). The pairwise head IS the value → PPO must switch to **consolidator + value_decoder**, not the glob fallback.
- **Pairwise label** = is_ahead at the **terminal horizon**: `label_ij = is_ahead_i`, valid only when `is_ahead_i ≠ is_ahead_j` (both players valid); ties masked. Both heads grounded in the same is_ahead signal.
- **Cache:** `final_rank` + `is_ahead` are already columns → **no 13 GB rebuild**.
- **Files:** `cross_entity.py` (`ValueDecoder`→`PairCompareHead`, re-add is_ahead head, rewrite `compute_loss_critic`) + `actor_critic.py` (V(s)=mean pairwise; flip to the value_decoder critic). Then a **combined pretraining notebook** (re-pretrain PairHead + pretrain the new critic) → PPO with the pretrained critic.
